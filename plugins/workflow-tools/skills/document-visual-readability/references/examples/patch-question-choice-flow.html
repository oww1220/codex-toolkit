NestJS request lifecycle

선택지 하나를 PATCH하면 서버 안에서 무슨 일이 일어날까?

이 엔드포인트는 선택지의 일부 필드만 받아, 질문 전체 상태와 합친 결과가 안전한지 먼저 검사합니다. 검증을 통과하면 선택지 한 행을 수정하고, 질문과 선택지 전체를 다시 읽어 공통 응답 형태로 돌려줍니다.

PATCH /v1/admin/questions/:id/choices/:choiceId
2개path parameter: 질문 ID와 선택지 ID
4개선택적 body 필드: 순서·문구·온도·정답 여부
검증 먼저현재 선택지와 병합한 다음 상태를 DB 쓰기 전에 검사
한 행 수정전달된 필드만 Prisma update data에 포함

Input

요청에서 들어오는 값

예시의 text와 isBest만 바뀌며, 생략한 필드는 기존 DB 값을 유지합니다.

HTTP 요청

PATCH /v1/admin/questions/question-1/choices/choice-2
x-admin-api-key: ********
Content-Type: application/json

Body

{
  "text": "조금 더 부드럽게",
  "isBest": true
}

Data movement

데이터는 이렇게 합쳐지고 이동한다

PATCH body에는 바꿀 값만 들어 있으므로, DB의 현재 선택지 전체와 합쳐야 수정 후 상태를 검증할 수 있습니다.

Happy path

요청이 움직이는 10단계

버튼을 누르면 현재 실행 중인 단계가 강조됩니다. 각 단계의 “실제 코드 보기”에서 근거 코드를 확인할 수 있습니다.

1

라우터가 대상 controller를 찾는다

Nest Router

@Controller('admin/questions')와 PATCH 경로를 합치고 URI versioning의 기본 버전 v1을 적용합니다.

실제 코드 보기 
@Controller('admin/questions')
@Patch(':id/choices/:choiceId')
2

Guard가 관리자 API key를 확인한다

AdminApiKeyGuard

x-admin-api-key가 서버 설정과 정확히 같아야 다음 단계로 갑니다. 설정이 없거나 다르면 controller는 실행되지 않습니다.

실제 코드 보기 
@UseGuards(AdminApiKeyGuard)

return typeof normalizedKey === 'string'
  && normalizedKey === expectedKey;
3

ValidationPipe가 body를 DTO로 검증한다

class-validator

네 필드는 모두 선택 사항이지만, 전달했다면 선언된 타입이어야 합니다. DTO에 없는 필드는 forbidNonWhitelisted 때문에 거부됩니다.

실제 코드 보기 
class UpdateQuestionChoiceRequestDto {
  @IsOptional() @IsInt()
  displayOrder?: number;

  @IsOptional() @IsString() @IsNotEmpty()
  text?: string;

  @IsOptional() @IsNumber()
  temperature?: number;

  @IsOptional() @IsBoolean()
  isBest?: boolean;
}
4

Controller가 입력을 service에 그대로 위임한다

Controller

@Param은 두 ID를, @Body는 검증된 DTO를 읽습니다. controller에는 비즈니스 분기가 없습니다.

실제 코드 보기 
return this.questionChoicesService
  .updateAdminQuestionChoice(questionId, choiceId, body);
5

질문과 기존 선택지를 함께 조회한다

Prisma read

부모 질문을 ID로 찾고, 검증에 필요한 선택지 relation을 displayOrder 순서로 가져옵니다. 질문이 없으면 404입니다.

실제 코드 보기 
client.question.findUnique({
  where: { id },
  include: { choices: { orderBy: { displayOrder: 'asc' } } }
});
6

choiceId가 이 질문에 속하는지 확인한다

Service branch

조회한 질문의 선택지 안에서 대상 ID를 찾습니다. 없으면 다른 질문의 선택지를 수정하지 않고 Question choice not found 404를 던집니다.

실제 코드 보기 
const targetChoice = question.choices
  .find((choice) => choice.id === choiceId);

if (!targetChoice) {
  throw new NotFoundException('Question choice not found');
}
7

PATCH 입력을 기존 값과 합친다

Pure merge

대상 선택지에만 전달된 필드를 덮어씁니다. text는 같은 지점에서 정규화하고, 나머지 선택지는 그대로 유지합니다.

실제 코드 보기 
const nextChoices = mergeQuestionChoices(
  question.choices,
  choiceId,
  input
);
8

수정 후 선택지 전체의 불변식을 검사한다

Domain validator

표시 순서는 양의 정수이면서 중복되지 않아야 하고, 선택지가 있다면 isBest인 항목이 최소 하나 있어야 합니다.

실제 코드 보기 
assertChoiceSet(nextChoices);

// 실패 예시
// Duplicate choice displayOrder
// At least one best choice is required
9

전달된 필드만 선택지 한 행에 UPDATE한다

Prisma write

undefined인 필드는 data에서 제외되므로 DB의 기존 값이 유지됩니다. 모든 검증이 끝난 뒤에만 쓰기가 실행됩니다.

실제 코드 보기 
this.prisma.questionChoice.update({
  where: { id: choiceId },
  data: {
    ...(input.text !== undefined
      ? { text: normalizeRequiredText(input.text) }
      : {}),
    ...(input.isBest !== undefined
      ? { isBest: input.isBest }
      : {})
  }
});
10

최종 질문을 다시 읽고 성공 envelope로 감싼다

Mapper + Interceptor

수정 후 질문과 선택지를 재조회하고 관리자 DTO로 매핑합니다. 전역 interceptor가 controller의 결과를 { success: true, data }로 감쌉니다.

실제 코드 보기 
return this.adminQuestionsService
  .getAdminQuestion(questionId);

// HttpResponseInterceptor
map((data) => ({ success: true, data }))
핵심: DTO 검증은 “요청 필드의 타입과 형태”를 확인하고, assertChoiceSet은 “수정 후 선택지 전체가 지켜야 할 규칙”을 확인합니다. 둘은 검증 대상이 다릅니다.

Branches

어디서 멈추느냐에 따른 응답

예외는 전역 HttpExceptionFilter가 공통 실패 형태로 변환합니다.

403

Guard 거부

관리자 API key가 없거나 서버 설정과 다르면 controller 전에 종료됩니다.

400

입력·도메인 검증 실패

DTO 타입 오류, 알 수 없는 필드, 순서 중복, 정답 선택지 부재가 해당합니다.

404

대상 없음

질문이 없거나, choiceId가 해당 질문의 선택지 목록에 없을 때 반환됩니다.

200

수정 완료

갱신된 선택지 전체를 포함한 질문 DTO가 성공 envelope 안에 반환됩니다.
