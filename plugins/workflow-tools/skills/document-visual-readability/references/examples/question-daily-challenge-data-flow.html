Malondo · Current implementation

질문과 데일리 챌린지는 어디서 만들어져 모바일까지 오는가?

관리자가 질문을 만들고 챌린지에 순서를 붙여 연결하면, NestJS가 Prisma 관계를 공개 DTO로 다시 조립합니다. 모바일은 그 응답을 Zod로 검증하고 React Query에 보관한 뒤 플레이 세션과 답안 기록까지 서버에 연결합니다.

전체 흐름 관리자 저장 공개 조회 모바일 플레이 응답 DTO 주의사항 서비스 읽는 순서
Admin이 작성질문 CRUD와 챌린지 CRUD는 별도 화면·API로 운영됩니다.
Join이 연결DailyChallengeQuestion이 질문 ID와 챌린지 안의 순서를 저장합니다.
API가 축소공개 응답은 게시 상태·감사 시각·관리용 순서를 제거해 모바일 형태로 바꿉니다.
Mobile이 검증생성된 Zod 계약을 통과한 데이터만 화면·플레이 상태로 들어갑니다.

Executive flow

전체 데이터 흐름

한 방향으로 보면 “작성 → 저장 → 공개 변환 → 캐시 → 플레이 기록”입니다.

핵심 경계: Admin 브라우저는 NestJS 관리자 API를 직접 호출하지 않습니다. 같은 origin의 Next.js Route Handler를 거치며, 서버 전용 ADMIN_API_KEY가 이 프록시에서만 x-admin-api-key로 주입됩니다.

Write path

관리자가 질문과 챌린지를 저장하는 흐름

질문을 먼저 공개 가능한 상태로 만든 뒤, 비공개 챌린지에 연결하고 마지막에 챌린지를 공개하는 순서입니다.

1

질문 생성·수정

폼 → React Query mutation → /api/admin/questions → NestJS /v1/admin/questions.

게시 질문은 선택지가 하나 이상이고, 그중 isBest: true가 하나 이상이어야 합니다.

2

챌린지 초안 생성

게시일·제목·설명을 저장합니다. 최초 생성은 질문이 없으므로 isPublished: true를 허용하지 않습니다.

3

공개 질문 검색

챌린지 화면은 질문 API를 isPublished=true로 조회해 연결 후보만 보여 줍니다.

4

질문 연결

{ questionId, displayOrder }를 보내 조인 row를 만듭니다. 비공개·중복 질문과 중복 순서는 거부됩니다.

5

순서 저장

전체 연결 목록을 PATCH합니다. API는 unique 충돌을 피하려 임시 음수 순서와 최종 순서를 한 transaction에서 적용합니다.

6

챌린지 공개

질문이 하나 이상이고, 모든 연결 질문이 공개 상태이며, 질문 ID·순서가 중복되지 않을 때만 공개됩니다.

Admin 기능 브라우저 경로 NestJS v1 경로 응답 data
GET 질문 목록·상세 /api/admin/questions[/:id] /v1/admin/questions[/:id] AdminQuestionResponseDto[] | AdminQuestionResponseDto
POST/PATCH 질문 저장 /api/admin/questions[/:id] /v1/admin/questions[/:id] 완성된 AdminQuestionResponseDto

POST 질문 연결 /api/admin/daily-challenges/:id/questions /v1/admin/daily-challenges/:id/questions 연결 후 챌린지 전체
PATCH 질문 순서 /api/admin/daily-challenges/:id/questions /v1/admin/daily-challenges/:id/questions 재정렬 후 챌린지 전체

↔

  • questionId: 연결할 Question
  • dailyChallengeId: 소속 챌린지

Read path

NestJS가 모바일용 공개 응답을 만드는 흐름

관리자 DTO를 그대로 보내지 않고 공개 mapper가 필요한 필드만 다시 선택합니다.

1

공개 챌린지 조회

isPublished: true인 챌린지를 publishDate desc로 하나 조회합니다.

2

관계 include

연결 질문 중 공개 질문만 포함하고, 연결 displayOrder와 선택지 displayOrder로 정렬합니다.

3

공개 DTO 매핑

챌린지에는 메타데이터와 질문 배열만, 질문에는 플레이 필드와 선택지만 남깁니다.

4

성공 envelope

전역 interceptor가 controller 결과를 { success: true, data }로 감쌉니다.

5

모바일 envelope 해제

requestJson이 data를 꺼낸 뒤 기능별 Zod schema에 전달합니다.

6

React Query 캐시

홈과 데일리 화면은 ['dailyChallenge', 'today'] 키를 공유해 같은 결과를 재사용합니다.

공개 endpoint 선택 기준 정렬 모바일 사용처
GET /v1/questions?mode=&category= 공개 질문 + 선택 필터 Question 순서 → Choice 순서 일반 모드 PlayScreen
GET /v1/daily-challenge/questions /questions와 같은 호환 alias Question 순서 → Choice 순서 현재 모바일 직접 호출 없음
GET /v1/daily-challenge/today 최신 공개 챌린지 1개 연결 순서 → Choice 순서 Home 카드, Daily 화면, Daily Play

Mobile runtime

모바일에서 질문을 고르고 플레이하는 분기

서버 데이터가 있으면 서버 세션까지 연결하고, 실패하면 화면 진행 자체는 유지합니다.

1. Daily Challenge 전달됨

dailyChallenge.questions가 비어 있지 않으면 이 배열을 사용합니다. 별도 일반 질문 조회는 비활성화됩니다.

2. 일반 플레이 또는 챌린지 조회 실패

GET /questions?mode=... 응답이 있으면 해당 공개 질문을 사용합니다.

3. 서버 질문도 없음

apps/mobile/src/data/questions.ts의 같은 mode 로컬 질문으로 진행합니다.

1

최대 5문항 선택

선택된 출처 배열을 복사해 섞고 최대 5개를 현재 플레이 질문으로 고정합니다.

2

세션 시작·복원

서버 질문이면 POST /question-play-sessions에 guest, mode, challenge ID, question ID snapshot을 보냅니다.

3

진행 중 세션 재사용

API는 사용자·챌린지·모드·질문 집합이 같은 PLAYING 세션을 찾아 재사용합니다.

4

답안 제출

POST /question-play-sessions/:id/attempts로 질문 ID와 선택지 또는 온도 추측을 전송합니다.

5

로컬 UI 즉시 진행

로컬 Zustand 채점·XP·피드백은 즉시 반영하고, 서버 attempt 실패는 화면 진행을 막지 않습니다.

6

결과 조회

완료 요약에 질문 세션 ID가 있으면 결과 화면이 GET /question-play-sessions/:id/result를 조회합니다.

Current-code caveats

현재 구현에서 알아둘 점

today는 실제 오늘 날짜를 비교하지 않습니다. getDailyChallengeToday()는 isPublished: true 중 publishDate desc 첫 항목을 반환합니다. 미래 게시일의 챌린지를 미리 공개하면 모바일에 먼저 노출될 수 있습니다.
공개 선택지 DTO에 정답 여부가 포함됩니다. QuestionChoiceResponseDto.isBest가 모바일 응답에 그대로 들어가므로 네트워크 응답만 보면 정답을 알 수 있습니다. 현재 모바일 즉시 피드백에는 이 값이 사용됩니다.
챌린지 조회 실패 시 시작 버튼의 실제 경로: Daily 화면은 챌린지 없이 openPlay('quiz')를 호출합니다. Play controller는 먼저 일반 공개 질문 API를 조회하고, 그마저 실패하거나 비어 있을 때 로컬 질문으로 내려갑니다.
서버 기록은 비차단: 질문 세션 시작이 실패하면 로컬 세션으로 계속하고, attempt 저장 실패도 화면의 채점·피드백을 되돌리지 않습니다. 따라서 오프라인 진행과 서버 기록이 다를 수 있습니다.

Service reading order

부모에서 순서를 읽고, 바로 아래에서 구현을 확인한다

2026-08-27 서비스 정리는 API·DB 동작을 바꾸지 않고 복잡한 7개 서비스의 내부 처리에 이름을 붙인 변경입니다. 부모에는 중요한 분기와 트랜잭션 경계를 남기고 전용 private 메소드는 다음 부모 전에 둡니다. 단순한 나머지 8개 서비스는 유지합니다.
