# Code Context Comments

## 핵심 원칙

주석은 코드를 다시 읽지 않고도 역할과 계약을 빠르게 파악하게 한다. 정확한 정보를 읽기 쉬운 구조로 남기며, 자명한 코드를 문장으로 반복하지 않는다.

## 작성 순서

1. 대상 선언의 구현, 호출자, 데이터 흐름, 기존 주석을 확인한다.
2. 코드만으로 알기 어려운 계약과 이유를 고른다.
3. 선언부 문서 주석에 역할과 계약을 모으고, 인라인 주석은 비자명한 분기나 실행 순서의 이유에만 둔다.
4. 현재 동작과 다른 주석은 갱신하거나 제거한다.
5. 주석만 훑어도 핵심을 파악할 수 있는지, 주석 때문에 코드 읽기가 더 느려지지 않는지 다시 읽는다.

## 읽기 쉬운 정보 구조

| 위치 | 담을 내용 |
|---|---|
| 첫 문장 | 선언의 핵심 역할 |
| 이어지는 문단 | 책임 경계, 호출 흐름, 상태 변화, 부작용, 실패 처리 |
| 목록·코드 블록 | 순서, 상태 전이, 단계별 판정 |
| `@param` | 값의 출처, 의미, 허용 조건 |
| `@return` | 반환값의 의미와 중요한 상태 |
| `@throws` | 예외가 발생하는 실제 조건 |
| 인라인 주석 | 코드만으로 드러나지 않는 순서·분기 선택의 이유 |

- 문단마다 한 주제만 다루고 문장을 짧게 쓴다.
- 프로젝트의 도메인 용어와 기존 주석 형식을 우선한다.
- 생소한 약어는 처음 한 번만 풀어 쓴다.
- 상세함과 가독성이 충돌하면 구현 세부사항을 덜어내고 계약과 이유를 남긴다.
- 문서·화면·테이블 식별자는 이해에 필요하고 안정적일 때만 기록한다.

## 정확성과 안전

- 코드 변경으로 계약이나 흐름이 달라지면 같은 변경에서 주석도 갱신한다.
- 서비스 경계, 보안 정책, 데이터 보관 여부, 외부 API 제약, 실패 격리처럼 숨은 의도를 우선 설명한다.
- 비밀키, 토큰, 실제 개인정보, 내부 접속정보를 주석이나 예시에 넣지 않는다.
- 생성 코드, 외부 라이브러리 코드, 마이그레이션 산출물은 수정하지 않는다.

## 주석을 생략할 곳

- 자명한 getter/setter, 단순 위임, 타입을 반복하는 DTO
- 이름만으로 충분한 한 줄 내부 함수와 익명 콜백
- 코드 한 줄씩을 한국어로 옮긴 설명

## 흔한 실패

- 모든 실행 줄에 주석을 붙임 → 선언부에 계약을 모으고 비자명한 이유만 인라인으로 남긴다.
- `학습 포인트:` 같은 말머리를 반복함 → 자연스러운 문장과 문단 구조를 사용한다.
- 긴 배경 설명이 핵심 역할을 가림 → 첫 문장에 역할을 두고 나머지는 주제별로 나눈다.
- 호출자를 확인하지 않고 의도를 추측함 → 실제 호출 경로에서 확인할 수 없는 내용은 쓰지 않는다.

Java/Javadoc의 정보 밀도와 문단 구성이 필요하면 [익명화된 Java 예시](references/java-javadoc-examples.md)를 읽는다. 예시는 복제용 템플릿이 아니라 판단 기준이다.
