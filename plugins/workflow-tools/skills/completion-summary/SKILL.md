# Completion Summary

## 무엇을 / 언제 (한 줄)

완료된 작업을 요약하거나, 이해가 막힌 변경의 맥락과 이어서 필요한 수정 방법을 설명할 때 사용한다. 기본은 한국어 채팅이며, 코드는 읽지만 수정 맥락을 이해하기 어려운 사용자를 기준으로 한다.

## 제약 (MUST DO / MUST NOT DO) — 스텝 위에 둔다

- ✅ 이미 적용한 변경과 앞으로 적용할 수정 제안을 명확히 구분한다. 완료 사실은 확인한 작업과 변경만 쓴다.
- ✅ 해당 코드의 어떤 문제가 어떻게 해결되는지 구체적으로 설명한다. “기존 구조를 따랐다”, “중복을 피했다” 같은 일반론만으로 끝내지 않는다.
- ✅ 실행한 검증과 실행하지 못한 검증을 구분해서 쓴다.
- ✅ 수정 대상이나 원하는 동작이 불명확하면 먼저 묻는다. 접근 가능한 코드와 대화를 확인하고, 필요한 근거가 없으면 관련 자료를 요청한다.
- ✅ 예시 코드는 실제 코드와 구분하고, 확인하지 않은 파일·함수 이름이나 원인을 지어내지 않는다.
- ⛔ 하지 않은 작업이나 확인하지 않은 효과를 완료한 것처럼 쓰지 않는다.
- ⛔ 기술 용어만 나열해서 사용자가 판단하기 어렵게 만들지 않는다.
- ⛔ 설명이나 수정 방법 요청만으로 파일을 변경하지 않는다. 실제 수정은 사용자가 별도로 요청한 범위에서 수행한다.
- ⛔ 커밋 메시지 작성 요청을 대신 처리하지 않는다.
- ⛔ 새로운 기능의 전체 구현 계획이나 HTML 문서 생성으로 범위를 넓히지 않는다. 요청하지 않은 긴 보고서, 파일 산출물, changelog를 만들지 않는다.

## 핵심 워크플로우

1. 사용자가 지목한 작업의 대화·코드·diff와 검증 기록을 확인한다. 이번 턴에 한정하지 않고 관련된 이전 작업까지 살핀다. 근거가 부족한 부분은 확정하지 않는다.
2. 사용자의 표현과 앞선 대화에서 궁금한 지점을 파악하고 필요한 설명 형식을 선택한다. 트리거와 질문 문구는 고정 호출어가 아닌 의도 판단의 예시이므로 정확히 일치할 필요는 없다. 변경 설명과 수정 방법을 함께 물으면 둘을 연결하되 완료 사실과 제안을 나눠 쓴다. 의도는 맥락에서 유추하되 수정 사실이나 추가 수정의 필요성을 추측으로 만들지 않는다.
3. 출력 전에 실제 변경, 수정 제안, 코드 예시, 실행한 검증과 제안하는 확인 방법이 혼동되지 않는지 확인한다.

### 일반 완료 요약

- 첫 문장에 무엇이 어떻게 달라졌는지 한 줄로 요약한다. 파일명보다 사용자가 이해할 수 있는 동작이나 규칙의 변화를 먼저 말한다.
- 변경 비교는 기본적으로 `항목 / 변경 전 / 변경 후`의 3열 표로 제시한다. 핵심 변경 2-5개를 기준으로 하되, 변경이 하나면 한 행만 쓴다. 파일 목록 대신 실제 동작이나 규칙을 비교하고 각 셀은 짧게 쓴다.
- 변경 이유가 표만으로 드러나지 않으면 표 아래에 짧게 설명한다. 긴 이유나 코드 블록을 표 안에 넣지 않는다.
- 실행한 검증 결과와 실행하지 못한 검증을 마지막에 짧게 명시한다.

### 변경을 이해하기 위한 추가 설명

- 막힌 부분에 집중해 `기존 문제 → 수정 이유 → 전후 동작`을 구체적인 사용 예시와 필요한 핵심 코드로 연결한다.
- 예: “중복 요청을 방지했다”에서 끝내지 않고, “저장을 두 번 누르면 요청도 두 번 나가던 것을, 처리 중인 추가 요청은 건너뛰게 바꿨다”처럼 설명한다. 예시는 확인한 실제 동작에 맞춘다.
- 전체 완료 요약을 반복하지 않는다. 수정 위치가 이해에 도움이 되면 확인한 파일·함수를 함께 제시한다.
- “뭐가 바뀌었어?”에는 전후 비교, “왜 이렇게 바꿨어?”에는 이유를 중심으로 답한다. 이유만 묻는 질문에 비교표를 강제하지 않는다.

### 어디를 어떻게 수정할지 안내

- 사용자가 수정 방법을 요청했거나, 설명 대상에서 확인된 문제로 추가 수정이 필요한 경우에만 수정 제안을 포함한다. 해당하지 않으면 제목까지 생략하고, 형식을 채우기 위해 제안을 만들지 않는다.
- 원하는 결과를 짧게 말한 뒤, 확인한 파일·함수에서 무엇을 어떻게 바꿀지 번호 목록으로 안내한다. 필요한 코드 예시와 확인 방법을 덧붙이며, 기존 구조를 활용한 최소 수정안을 기본으로 한다.
- “조건 처리를 개선하세요”처럼 끝내지 않고, 확인한 코드에서 어떤 조건을 어디서 어떻게 바꿔야 하는지 설명한다.
- 아직 적용하지 않은 내용은 `수정 제안`으로 표시한다. 짧은 변경 전후 코드나 적용 예시가 도움이 되면 포함한다.
- 코드가 없어 구체적인 위치를 정할 수 없으면 필요한 소스를 요청한다. 안내 가능한 일반 원리와 실제 코드 확인이 필요한 부분을 구분한다.
- 제안한 수정 뒤 정상 동작과 관련 실패 상황을 어떻게 확인할지 안내하되, 이를 이미 실행한 검증처럼 쓰지 않는다.

## 출력과 가독성

- 채팅 답변에만 정리한다. 기본 읽기 순서는 `핵심 한 줄 → 변경 비교 → 필요한 이유·코드 → 수정 제안(해당할 때만) → 검증 또는 확인 방법`이며, 질문에 필요한 부분만 보여준다.
- 완료된 변경과 아직 적용하지 않은 제안은 같은 표에 섞지 않는다. 필요한 곳에 `변경 완료`, `수정 제안`, `미검증`을 표시해 상태를 구분한다. 제안하는 확인 절차는 `확인 방법`으로 쓴다.
- 굵은 글씨는 핵심 결론과 상태 표시에만 사용한다. 표에서 설명한 내용을 아래 문단에서 반복하지 않고, 빈 섹션이나 “수정 제안 없음” 같은 형식 채우기를 하지 않는다.
- 사용자가 지정한 형식과 길이를 우선한다. 한 문장 요청이나 짧은 후속 질문에는 전체 구조나 표를 강제하지 않는다.
